Alert

Say something about the page that stays until it is no longer true.

Use when

  • A condition that holds for the whole page or region — a source is stale, eleven items are unanswered, the run failed.
  • A message with a way out of it: put the action in AlertActions, beside the problem it fixes.
  • Set live when the banner appears after load; danger and warning announce assertively, the rest politely.

Not when

  • Confirming an action the person just took, which needs no further attention → Toast. A toast reports an event and leaves; an alert reports a condition and stays.
  • The region has nothing to show, failed to load, or is not allowed → State. A state replaces the content it stands for; an alert sits above content that is still there.
  • A note inside prose that qualifies what is around it → Callout. A callout is a rule beside text at reading scale; a tinted banner would make it an alert it is not.
  • The person must answer before anything else can happen → Dialog. A dialog takes focus and must be dismissed; an alert can be read past.
  • A form step has fields that failed validation → ErrorSummary. The error summary links each problem to its field and takes focus on submit.

Callout

Set a quiet aside inside prose.

Use when

  • A note, caveat or rule that qualifies the text around it — "Figures exclude the March import."
  • A short absence or warning at reading scale: tone="warning" tints the rule, nothing else.

Not when

  • The message is about the page or a region, not the paragraph → Alert. An alert is a banner with a tone and an action; a callout is a rule beside text.
  • The region has nothing to show → State. A state says why the content is absent and what to do; a callout assumes there is prose around it.
  • A hint that belongs to one form field → Field. A field hint is tied to its control by aria-describedby; a callout is not.
  • A short status word → Tag. A status is one or two words in a tag, never a sentence.

ErrorBoundary

Keep one broken region from blanking the app, and say plainly that it could not be shown.

Use when

  • Around a routed page, inside the frame, so the header and navigation stay when the page throws: <ErrorBoundary resetKey={path}>, and leaving the page recovers it.
  • Around a panel that renders data it does not control — a detail pane, a chart, an embedded preview — with the record id as resetKey.
  • Hand the error to onError for the log. The person sees State kind="error", never the error text.

Not when

  • A fetch failed or a source did not answer → State. A failed fetch is a state the screen expected and renders itself, with a retry; a boundary is for a render that threw.
  • The content is there and something about it is wrong or stale → Alert. An alert sits above content that still shows; a boundary replaces content that could not be drawn.

Connection

Show an integration and the state it is in, with the way to fix it.

Use when

  • A list of connected systems, each with its mark, name, a note and its state — connected, degraded, error, pending or off.
  • The state is a word in ConnectionStatus; the dot is decorative, so colour is never the only signal.
  • Actions to connect, reconnect or configure sit on the row in ConnectionActions.

Not when

  • The status is not about an integration → Tag. A tag is the general status word; ConnectionStatus has only the integration states.
  • The problem needs the reader to act before carrying on with the page → Alert. An alert is an inline banner with a title, body and action for one problem.
  • The thing on the row is an API key or a secret → KeyList. Keys have a fingerprint, scopes, last use and expiry; a connection has none of those.

Progress

Show how far a task has got toward done.

Use when

  • An upload, an import or an export with a known fraction complete — pass value 0–100.
  • A task that is under way with no known fraction: omit value for the indeterminate bar.
  • ProgressRing where a bar does not fit — a compact figure beside a title.

Not when

  • A level that is simply true — usage, capacity, a score against a target → Meter. role="meter" reports a level; a progress bar says a task is advancing, and swapping them misreports what is happening.
  • One row's live work in a list or table, with where it is and a count → LiveProgress. Live progress carries the pulse, the place being worked and the count, and turns into a tag when done or failed.
  • The person is moving through named steps → Stepper. A stepper names each step and its state; a bar only says how much.
  • A short wait inside a control with nothing to measure → Spinner. A spinner is the smallest "still working" and takes no room.

Skeleton

Hold the shape of content that is still being read.

Use when

  • A page or a list is loading and its layout is known — lines of text, a title, a block, an avatar circle.
  • Inside a region that announces its own loading (aria-busy); each bar is always aria-hidden.

Not when

  • There is nothing to show → State. A skeleton means "still reading" and never "nothing here"; an empty state names the cause and the way out.
  • The read failed → State. A skeleton never tells you it has finished; an error state says what went wrong.
  • The wait is short and the layout is not known → Spinner. A spinner marks a brief wait without promising a shape.
  • A section is being written by a run right now → Live. LiveSection and LiveMark say the section is being written, in words.

Spinner

Show that a short wait is under way, where its result will appear.

Use when

  • A brief wait inside a control or a small region — a button submitting, a panel refreshing.
  • Decorative by default: the surrounding region carries aria-busy; pass label only when it stands alone.

Not when

  • The shape of the content that is loading is known → Skeleton. A skeleton holds the layout so nothing jumps when the content lands.
  • The work has a known amount done and to do → Progress. A progress bar says how far along it is; a spinner only says "busy".
  • An agent or a run is working on something the reader is watching → Live. Live work is drawn where the work is, with a word beside the pulse.
  • A button is submitting → Button. The button has its own loading state (.is-loading) and keeps its label and width.

State

Stand in for content that is loading, empty, partial, failed, denied or done.

Use when

  • A region has no content to show and needs to say why: kind is loading, empty, partial, error, denied or success.
  • A figure or list built from some sources but not all — partial says which are missing.
  • An empty list that names its cause and offers the way out in StateActions; art gives an empty place a line drawing.

Not when

  • The content is there and something about it needs saying → Alert. An alert sits above content that is still shown; a state replaces it.
  • The region is still loading and its shape is known → Skeleton. A skeleton holds the layout while it reads; State kind="loading" is for when the shape is not known.
  • A sign-in or access page that stands before the product → Entry. A way in is not an empty state; read as one it looks like a dead end.
  • Confirming a quick action that worked → Toast. A success state replaces a whole region; most successes only need a toast.

Stepper

Show where someone is in a named sequence of steps.

Use when

  • A multi-step task where each step is an act the person performs — markers, one per step.
  • A sequence that is a position the work is somewhere in — rail, which fills what is behind.
  • A step that was refused or broke: failed, never left at current or marked complete.

Not when

  • Building the whole multi-step form, with back and forward → Flow. The flow shell already holds a vertical stepper, one content region and the footer.
  • How much of one task is done, with no named steps → Progress. A bar says how much; a stepper says which.
  • Many agents or items moving through waiting, working and done at once → Lanes. Lanes show many items by state; a stepper is one sequence.
  • Events that already happened, in order → Timeline. A timeline is history; a stepper is position in a plan.

Tag

Say in one or two words what state a thing is in.

Use when

  • A row, card or heading reports a status — Draft, Approved, At risk, Failed — and the variant maps to its meaning.
  • A quiet marker on a dense row: dot puts a filled dot before the word instead of a tint.

Not when

  • The word is something the reader can press to do something → Button. A status is a tag and an action is a button; where both sit on one row they must differ in shape, not only in colour.
  • The value is a neutral attribute — an owner, a standard, a type — that may narrow the list → Facet. A tag carries no status here and is decoration; a facet is a name and a value, and narrows when pressed.
  • The state is an integration being connected, degraded or off → Connection. ConnectionStatus carries the integration states with a decorative dot and the word.
  • The status needs a sentence to explain it → Alert. A tag is one or two words; prose belongs in an alert, a hint or a state body.

Toast

Confirm that something just happened, briefly, without taking focus.

Use when

  • The result of an action the person took — "Saved", "Invite sent", "Export ready" — with at most one way to take it back: ToastAction for Undo, before ToastClose.
  • An event that happened elsewhere while they work, worth a glance and no more.
  • Rendering the surface yourself; mount ToastRegion once, near the root, before any toast is added.

Not when

  • You want to raise a toast from anywhere in the app with timers handled → ToastProvider. The provider owns the queue, the timeout and the pause on hover; Toast is only the surface.
  • The condition is still true after the moment passes — a failed source, a stale figure → Alert. A toast leaves; a condition that leaves with it is a condition nobody can find again.
  • The person has to decide something before going on → Dialog. An action in a toast is right for undo, not for a decision: a toast is polite and can be missed, and a decision needs a modal that holds focus.
  • An agent proposes a change and the person has to confirm or approve it → ConfirmCard. An action in a toast is right for undo, not for a decision; the confirm card holds the values and waits in the conversation until it is answered.
  • The region the action was meant to fill is empty or failed → State. The result belongs where the content would be, not in a corner.

ToastProvider

Raise toasts from anywhere in an app, with the queue and timers handled.

Use when

  • Wrap the app once and call useToast().toast({ title, tone }) from any component.
  • Toasts should time out, pause while the pointer is over them, and cap at a few on screen.
  • Undo after the fact: toast({ title, action: { label: 'Undo', onAction } }). A toast with an action stays until dismissed (it defaults to duration: 0), and its button is announced with it and reached by Tab.

Not when

  • You render the toast markup yourself, or in static HTML → Toast. The provider renders Toast for you; use the parts directly only when you own the queue.
  • The person has to decide something — confirm a delete, choose between two outcomes → Dialog. An action in a toast is right for undo, not for a decision; a decision needs a modal that holds focus until it is answered.
  • An agent asks the person to confirm or approve a change → ConfirmCard. An action in a toast is right for undo, not for a decision; the confirm card shows what will change and waits for an answer.
  • The message describes a condition rather than an event → Alert. A queued toast times out; a condition has to stay on the page.
